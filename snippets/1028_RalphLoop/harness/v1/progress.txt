2026-06-30T13:48:00Z - Implemented "Weighted grade average calculation and
display" (second optional feature).

Weighting is by each subject's lessons_per_week (already on the subjects
table from the subject-management feature) - a subject taught more hours
per week counts proportionally more toward the average, which is the usual
meaning of "weighted average" in this kind of Hungarian-style report-card
system. Computed from year_end_grades (the one-final-grade-per-assignment
table), not the running grades table, since a year-end grade is the
authoritative per-subject result for a year.

Backend (backend/):
- backend/src/routes/averages.js: new /api/averages router, mounted in
  server.js.
  - GET /api/averages/:studentId (optional ?year=) - requireAuth only (no
    requireRole): a student may view only their own average (403
    otherwise), teachers/administrators/super_administrators may view any
    student's average (consistent with how classes.js opens roster reads to
    "any authenticated user" and grades.js gives admins full oversight).
    404 if studentId doesn't reference a role='student' user.
  - Joins year_end_grades -> class_subjects -> subjects to get each grade's
    subject and lessons_per_week, computes
    weight = max(lessons_per_week, 1) per row (floored at 1 so a subject an
    admin forgot to set a weekly-lesson count for still contributes instead
    of being silently dropped from the average), then
    average = sum(value*weight)/sum(weight). Returns {studentId, year,
    average, totalWeight, breakdown: [{subjectId, subjectName, year, value,
    weight}]}; average is null if the student has no year-end grades yet
    (optionally none matching the ?year= filter).

2026-06-30T14:06:00Z - Implemented "Timetable management" (fifth optional
feature).

A weekly lesson schedule built on top of the existing class_subjects
assignment (which already encodes class+subject+teacher+year), so a
timetable entry just adds *when* that lesson happens: day of week and a
period slot, plus an optional room. Used period numbers (1-10) rather than
start/end time strings to avoid time-overlap interval math entirely -
"same day + same period" is a simple equality check, which matters here
since there is no way to execute/test the comparison logic in this sandbox.

Backend (backend/):
- backend/src/db/index.js: new timetable_entries table (id,
  class_subject_id FK->class_subjects ON DELETE CASCADE, day_of_week
  INTEGER CHECK 1-7 [1=Monday..7=Sunday], period INTEGER CHECK 1-10, room,
  created_at), UNIQUE(class_subject_id, day_of_week, period) so the same
  assignment can't be double-entered at the same slot.
- backend/src/routes/timetable.js: new /api/timetable router, mounted in
  server.js, with a SELECT_WITH_JOINS mirroring classSubjects.js's pattern
  (joins class_subjects/classes/subjects/users so responses include
  classIdentifier/subjectName/teacherName/classId/teacherId/year).
  - GET / (optional ?classSubjectId=&classId=&teacherId=&dayOfWeek=) - any
    authenticated user, same "open roster read" convention as
    class-subjects.js's GET (timetable data isn't sensitive and needs to be
    visible to the affected students/teachers, not just admins).
  - POST / - administrator/super_administrator only; body {classSubjectId,
    dayOfWeek, period, room}. Beyond the UNIQUE-constraint duplicate check,
    a findConflict() helper checks for *other* class_subjects sharing the
    same class_id or teacher_id already scheduled at that day+period and
    returns 409 ("The class"/"The teacher" already has a lesson scheduled
    at this day and period) - prevents double-booking a class with two
    subjects at once, or a teacher with two classes at once.
  - PATCH /:id, DELETE /:id - same role restriction and conflict checks
    (PATCH excludes the entry's own id from the conflict search), admin
    only since scheduling is treated as an admin task here (consistent with
    class_subjects.js's POST/PATCH being admin-only too).
